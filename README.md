# Civil Estimator

Standalone Streamlit tool for civil construction takeoff and BOQ generation from structural drawings.

**Current state: Phase 2 complete.** Structured input form → 10-sheet Excel workbook with formulas, wastage, and SAR costing, plus a local Qwen2.5-VL:7b vision extractor that pre-fills the form from a drawing PDF.

Upload a drawing, get a workbook:

```bash
ollama serve && ./bin/app.sh
```

Then open **Drawing → BOQ** in the sidebar. Headless equivalents:

```bash
venv/bin/python run_pipeline.py --derive all --audit-sheet   # one drawing
venv/bin/python run_pipeline.py --batch drawings/            # a whole set + roll-up
```

`./bin/app.sh` is still the recommended launcher — it uses `venv/bin/streamlit`
and the pinned dependency versions. But `streamlit run Home.py` now works too:
`sitepath.py` runs first in every entry point and appends the venv's
site-packages as a fallback, so the framework Python can borrow PyMuPDF instead
of dying with `ModuleNotFoundError: No module named 'fitz'` the moment someone
opens the Extract page.

### Excel output — 10 sheets (plus optional extras)
1. **Summary** — flat BOQ, all lines, wastage formulas in-cell
2. **Pedestals** — per-pedestal breakdown (P1–P7, concrete, formwork, rebar)
3. **Slab** — per-slab breakdown
4. **Sump** — per-sump breakdown
5. **Joints** — expansion/contraction/construction + accessories
6. **Coating** — epoxy areas × coats
7. **Embedments** — insert plates, anchor bolts, dowels
8. **Rebar_BBS** — bar-by-bar (coefficient rows + manual BBS rows)
9. **Assumptions** — editable wastage %, rebar unit weights (reference), source drawing filename, generated timestamp
10. **Costing** — rates × quantities, SUMIF subtotals by category, grand total

Every sheet's title block shows: project name, drawing no, revision, prepared-by, created timestamp (identical across all sheets in one workbook run).

Phase 2 appends three more when relevant, always **after** the ten so the
template keeps its identity: **Verification** (sign-off against the drawing),
**Derivation** (the arithmetic behind derived quantities) and **Extraction_Log**
(every model call).

### Output filename format
`{sanitised_drawing_no}_{YYYYMMDD}_{HHMM}.xlsx`
Example: `MD-522-8110-EG-CV-LAD-0107_20260906_1430.xlsx`

### BOM element types supported
1. Excavation (with soil type)
2. PCC / Blinding
3. Pedestals (rectangular, any grade, any coefficient)
4. Grade Slab
5. Sump / Pit (base + 4 walls)
6. Curb Wall / Dyke Wall
7. Formwork (auto-derived + loose entries)
8. Rebar — coefficient path (kg/m³) OR manual BBS bars (both allowed, warns on double-count)
9. HDPE Liner
10. Compacted Soil / Fill
11. Epoxy / Acid-Resistant Coating (with coats)
12. Joints (expansion, contraction, construction + accessories)
13. Embedments (insert plate, anchor bolt, dowel, sleeve)
14. Waterstop (standalone runs)
15. Sump Ancillaries (gratings, drain pipes, covers)

### Wastage defaults (editable per run)
- Concrete 3%, Rebar 5%, Formwork 10%, HDPE 8%, Epoxy 15%, PCC 5%, Soil 10%
- Earthwork excavation and Embedments = 0% (procured discrete)
- Joint accessories inherit joint length (0% wastage on run length)

## Workflow (Phase 1)

1. **Home page** — enter project name, drawing no, revision, prepared-by. Attach the PDF drawing (reference only in Phase 1). Optionally save project state to JSON for cross-session persistence.
2. **1_Input** — 14 tabs, one per element type. Use `st.data_editor` grids to add/edit/delete rows.
3. **2_Review** — adjust wastage % if needed. See live BOM preview, warnings (e.g., rebar double-counting), and rollup totals.
4. **3_BOM** — see KPIs (total concrete/rebar/formwork/excavation), full BOM table, and rebar BBS. Click **Generate Excel BOQ** → download workbook.
5. **4_Costing** — enter unit rates per (category × unit). Rates persist in `data/rates.db` and pre-fill on future projects. Excel Costing sheet uses saved rates.

# Phase 2 — Local vision extraction (delivered)

Reads an engineering drawing PDF with **Ollama + `qwen2.5vl:7b`**, entirely on
the laptop. No cloud APIs, no fine-tuning, no new Python dependencies.

## Run it

```bash
ollama serve                 # once; the app warns if it is not up
./bin/app.sh                 # the whole flow in a browser
```

**Use `./bin/app.sh`, not `streamlit run Home.py`.** `streamlit` on PATH is the
system framework Python, which has no PyMuPDF — the Extract page dies with
`ModuleNotFoundError: No module named 'fitz'`. The launcher uses `venv/bin/streamlit`.
Pages work on both Streamlit 1.39 and 1.58 via `extractors/st_compat.py`.

Headless, for a whole folder or a script:

```bash
venv/bin/python run_pipeline.py                      # root PDF → output/*.xlsx
venv/bin/python run_pipeline.py drawing.pdf --profile quick
venv/bin/python run_pipeline.py --extract-only       # JSON only
venv/bin/python run_pipeline.py --from-json output/x_extraction.json
```

## The page

`pages/0_Extract.py` is the whole job on one page: **upload PDF → preview →
extract → correct the numbers in a grid → download the workbook.** Pedestal
heights are not printed on these drawings, so the grid asks for them explicitly
before the workbook is worth trusting. `1_Input` … `4_Costing` remain for
manual entry and rate work.

## How it works

**Locate the text first, with geometry, not the model.** The drawing has no text
layer — 83,981 vector paths, zero extractable characters, so `pdfplumber`
returns nothing. But outlined glyphs still *look* like glyphs: small, compact
paths sitting in rows. Clustering them finds every text block on an A0 in ~1 s
with **zero model calls** (`extractors/vector_text.py`). If the PDF *does* have a
text layer, it is read directly and Stage 2 costs nothing at all.

**Then send only the text.** Candidate callout blocks are cropped, scaled so
their glyphs are ~22 px tall, and packed two-column into montages under the
latency cliff. 38 candidate blocks become **4 images**.

**The model transcribes; regex interprets.** One prompt asks for a verbatim
transcript of every crop. `callout_grammar.scan_lines` then applies separate
grammars for pedestals, curb walls, sumps, levels, insert plates, epoxy specs,
rebar callouts and thickness notes. Adding an element type costs **no extra
model calls**.

**Retry on truncation.** The model sometimes transcribes some crops and stops —
which is detectable, because the prompt states the crop count. A short montage
is re-sent split in two, bounded at two splits. This is what took recall from
4/5 to 5/5.

**Merge is non-destructive.** Anything already entered wins; re-merging is
idempotent. Element types the drawing does not fully dimension (a curb wall
gives thickness and height but never its run length) are *surfaced, never
merged* — guessing the missing half is how a BOQ goes wrong quietly.

## Signing in

The app is behind a shared password. Set one before first use:

```bash
venv/bin/python bin/set_password.py
```

It prompts twice with hidden input and writes a **PBKDF2-HMAC-SHA256 hash and a
random salt** to `.streamlit/secrets.toml` (already gitignored, chmod 600). The
password itself is never stored, printed, or passed as an argument — a
command-line argument would land in your shell history.

**What this is:** a door, so a colleague cannot open the tab and start editing an
estimate. **What it is not:** protection for tender data. Streamlit runs locally
with your own file access, so anyone who can reach the machine can read
`output/` and the project JSONs regardless. Treat it as an office-door lock, not
a safe.

Every page carries its own gate. Streamlit runs each page as a separate script,
so a login on the home page alone would be bypassed by navigating straight to a
page URL — `tests/test_auth_and_ui.py` asserts the gate exists on all six pages
and runs before any page content. Five wrong guesses trigger a cool-off, and an
app with no password configured **refuses entry** rather than failing open.

## Branding and layout

`bin/build_assets.py` regenerates the PNG logo variants from
`Logo/GI_Logo.tiff`. The master is a 12 MB TIFF, which browsers cannot render at
all, so it is never served — the sidebar, login card and favicon each get a
correctly sized PNG that is small enough to inline as a data URI.

The brand header and the workflow step bar are **pinned** to the top of every

Streamlit wraps each element in `stElementContainer` (the older
`element-container` test id no longer matches), and its own toolbar is
`position: fixed` at 60 px, so a sticky header at `top: 0` pins *underneath* it
and disappears. Both are asserted in the tests.

## Checking the output against the drawing

An estimator handed a spreadsheet and an A0 has no way to check one against the
other except by hunting. Two artefacts close that:

* **Check print** (`output/<drawing>_check.png`) — the sheet with every extracted
  value boxed, numbered and colour-coded by confidence. Print it, sit it beside
  the drawing, mark it up.
* **Verification sheet** (11th sheet in the workbook) — one row per extracted
  value with its **verbatim callout** and its **drawing grid reference**
  (e.g. `D-7`), plus blank *Correct value / Verified by / Date* columns.

The grid is **measured from the sheet**, not assumed: border label positions are
clustered to find the real cell pitch. On the reference A0 that is 16 × 16 — and
the row letters include I and O, which the ISO convention normally omits.
Assuming the convention would have put every reference below row H off by one.

**Locating a value is harder than reading it, and the failure is silent.** Three
attempts, each defeated by measurement:

1. *Map transcript position to crop position.* Wrong — on a two-column montage
   the model returned the top-**right** crop first, so text was attributed to the
   wrong patch of drawing.
2. *Trust position when the counts match.* Still wrong, for the same reason.
3. *Print a number beside each crop and ask for it back.* Better, but the model
   **repeats itself**: it reported the same P1 callout under crop 1 *and* crop 5
   of one montage, and again on a montage that does not contain P1 at all.

So a location is **voted on** across sightings. A clear majority wins; a tie
means we do not know, and the value appears in the check print unboxed with a
note saying why. On the reference drawing that leaves 4 of 5 pedestals located
and P1 explicitly unlocated — which is the correct answer, because the evidence
genuinely conflicts. An engineer can find an unboxed value; one sent to the
wrong grid square may simply tick it.

`docs/VERIFICATION_PLAN.md` is the session plan: what to check, in what order,
and what "accurate enough" means.

## Two kinds of PDF, two routes

Not every issued drawing is the same animal. Of the eleven sheets in `Drawings/`:

| Route | Sheets | Why |
|---|---|---|
| **Text layer** | 0101–0105 | 5,900–8,200 characters of real text — read directly |
| **Vision** | 0106, 0107, 0115, 8120-0105 | text outlined to curves, nothing to read |
| **Vision** | 8120-0101, 89MH-0001 | 141 and 328 stray characters — *not* a text layer |

When a sheet keeps its text, reading it is better in every way: exact
characters, exact coordinates, **zero model calls**, and it returns in 0.2 s
instead of five minutes. The extractor originally looked only at vector path
geometry and walked straight past all of that, which is why five drawings
"could not be extracted".

Detection is by **volume**, not presence. Two sheets carry a scattering of
border labels while being entirely outlined; treating those as text sheets would
skip the vision path and return nothing instead.

**Picking the sheet's own drawing number** is the subtle part. A sheet names
several — the references table lists what it depends on, details point
elsewhere. Counting occurrences gets it wrong: 0102 reported 0101, and 0105
reported 0104, because a referenced drawing can appear more often than the
sheet's own number. Position settles it — the ISO border repeats the number in
the **top-left corner**, and that occurrence is right on all five sheets.

**Position marks.** The plan sheets carry one mark per element (P1, P2, F1) with
a "FOR DETAILS REFER DWG …" note, while the sizes live on the details sheet.
Counting the marks is how an estimator gets the quantity, so they are counted —
but reported for review only, never as a BOQ quantity. An element drawn in both
plan and section is labelled twice, and an unlabelled one is not counted at all.

## Consolidated workbook for a set

```bash
venv/bin/python run_pipeline.py --batch Drawings --derive all
```

Writes `output/SET_BOQ.xlsx` alongside the per-drawing workbooks:

| Sl. # | Description | UoM | 0101 | 0102 | … | Total | Assumptions |
|---|---|---|---|---|---|---|---|

One row per distinct item, one column per drawing, grouped by category, with the
full drawing number under each short code. Behind the Summary sit detail sheets
named by drawing and activity — `0107_Concrete`, `0107_Rebar`. Excel caps sheet
names at 31 characters and a Maaden number is 26 on its own, so tabs use the
serial; where two areas share a serial the tab becomes `8110-0107` / `8120-0107`,
because Excel renames duplicate tabs silently and the reader loses their place.

**Assumptions are shaded, not blended in.** Any quantity that came from a
derivation rule or a placeholder pedestal height is highlighted and named in an
Assumptions column, so an engineer can see at a glance which numbers were read
off a drawing and which were worked out.

## Correction loop

The team marks up the **Verification** sheet — it already lists every extracted
value with its verbatim callout, grid reference and blank *Correct value /
Verified by / Date* columns — and the marked-up files come back in:

```bash
venv/bin/python bin/ingest_corrections.py output/reviewed/*.xlsx
```

Three things happen, in increasing order of usefulness:

1. **Scoring** — accuracy per item type and per drawing, written to
   `output/accuracy/`, so a change can be shown to help rather than argued about.
2. **Examples** — a drawing whose pedestal rows were all confirmed becomes a
   verified few-shot example for sheets in the same family. One wrong row
   disqualifies it: an example is ground truth for every later run, so a
   half-right one teaches the mistake.
3. **Grammar gaps** — any corrected value whose callout the regex could not
   parse is listed. This is the highest-value output: a callout shape the
   grammar misses is missed on *every* drawing until a pattern is added, and
   unlike model behaviour a regex fix is deterministic, permanent and testable.

**This is not fine-tuning**, and the loop does not pretend to be. Fine-tuning
qwen2.5vl needs a 24 GB GPU and a hundred labelled sheets, neither of which is
on this machine. The three mechanisms above are what a local setup can genuinely
learn from, and they take effect on the very next run.

## Derived quantities

A foundation layout prints the slab extent and the pedestal callouts. It does not
print the excavation volume, the blinding area, the liner area or the joint run —
an estimator works those out by hand. `core/derivation.py` does that arithmetic
explicitly:

| Rule | Formula |
|---|---|
| Excavation | footprint + working space each side × (slab + blinding + fill) |
| Compacted fill | footprint × fill thickness |
| PCC blinding | footprint + offset each side × blinding thickness |
| HDPE liner | slab footprint |
| Epoxy coating | slab top area × coats |
| Curb wall | run = slab perimeter, at the callout's height and thickness |
| Contraction joints | panel grid across the slab |

Every rule shows its formula and its parameters, seeds its defaults from what
the extractor actually read (a `CURB WALL 150THK x 150HIGH` callout sets the curb
rule), and is **off until you enable it**. A derived quantity is an assumption,
and an assumption that reaches a priced BOQ without someone accepting it is how a
tender goes wrong. The workbook records them on a **Derivation** sheet with the
arithmetic.

On the reference drawing this takes the BOQ from 2 of 15 element types to 9.

## Hard-won constraints (all asserted in tests)

* **Latency cliff between ~1600 and ~1900 prompt tokens.** 1.3× the tokens costs
  6× the time (0.95 MP → 47 s, 1.20 MP → 318 s). Cap images by *total pixels*,
  never longest edge — a near-square tile sized by its longest edge carries 4×
  the pixels of a wide strip sized the same way.
* **Cost is per call, not per pixel**, below that cliff. Every sub-cliff call
  measured 45–55 s. So the win is *fewer calls*, which is what montages buy.
* **Never stack prohibitions in a prompt.** Adding three "ignore X / return empty
  if none" rules took recall from both-callouts-correct to `{"pedestals": []}` on
  the identical image. A 7b model given several reasons to withhold takes the
  null answer, and it fails *silently* — a clean, confident, empty result.
  `SUPPRESSIVE_PHRASES` records the wording; a test fails if it returns.
* **Rotation.** `get_drawings()` reports coordinates in *unrotated* PDF space.
  This sheet is stored portrait with /Rotate 270; without `page.rotation_matrix`
  every text block lands in the wrong place, and it looks plausible.

## Extraction is driven by the drawing, not by a list of element types

The first version of the extractor looked for pedestals, grade slabs, sumps and
pits, because those are what the first drawing contained. That is the wrong way
round, and this set proved it: five of eleven sheets carry no pedestal and no
slab, and every one of them was reaching the workbook with an empty column.

`extractors/discovery.py` fixes it by never asking "is there a pedestal here".
It asks what has a **specification** printed beside it, and takes the item's
name from the drawing's own words. The rule that keeps this from scraping every
string on an A0:

> An item worth a BOQ line carries a number on the drawing.

A thickness, a diameter, a bar count, a bolt size, a pair of plan dimensions, a
compaction percentage. Text with no number is a title, a reference or a
centreline label — it tells an estimator where to look, not what to buy.

The unit follows from **what was measured**, which is why an item nobody
enumerated still gets a sensible one:

| Printed on the sheet | Item | UoM | Quantity |
|---|---|---|---|
| `30 THK GROUT` | Grout, 30 mm thick | m² | area to confirm |
| `40 THK BITUMEN SCREED` | Bitumen Screed, 40 mm thick | m² | area to confirm |
| `MANHOLE 1200x1200x1800` | Manhole 1200x1200x1800 | m³ | 2.592 per unit |
| `16-D25` | D25 bars — 16 Nos per element | Nos | 16 |
| `D10 @ 150 LINK` | D10 bars @ 150 c/c | m | run length to confirm |
| `AR-(4)-B-M36-1345-N2` | Anchor assembly AR M36 x 1345 | Nos | 4 |
| `20mm DIA LUGS` | Lugs, 20 mm dia | Nos | count to confirm |

Nothing is invented. A blank quantity means the sheet states the specification
but not the extent, and the row says exactly which figure is missing. Every row
keeps its grid reference and the verbatim text it came from, so a reviewer can
find it on the sheet in seconds.

`tests/test_discovery.py` includes a guard that parses `discovery.py` with `ast`
and fails if any string literal in the **code** (docstrings and comments
excluded) names an element type. The moment one does, the next drawing that
omits it is back to producing nothing.

### Where it shows up

* **Summary** of `SET_BOQ.xlsx` — a `READ FROM THE DRAWINGS — CONFIRM BEFORE
  PRICING` block, one row per item, one column per drawing. Not totalled across
  the set: "16 bars per element" and "0.972 m³ per unit" are not addable.
* **`<code>_Drawing items`** — one sheet per drawing, grouped by how each item
  was measured, plus the strengths quoted in the sheet's general notes and the
  heights implied by its levels (`BOBP EL. 98.380` over `BOC EL. 95.500`).
* **`Drawing_Items`** — the same, appended to a single-drawing workbook.
* **Drawing → BOQ** — the same table, in an expander above the review grid.

A drawing whose text layer survived costs **no model calls at all**, so the CLI
no longer refuses to run when Ollama is down if every sheet in the batch can be
read from text.

## Extraction runs outside the app

Reading twenty drawings used to happen inside the Streamlit script. Streamlit
cannot redraw or accept a click while a script is running, so the tab froze for
the length of the batch, and a cancel button was not merely missing but
impossible — there was no moment in which the app could notice it.

Now the app only ever writes to a queue. A separate process does the work, and
one command owns both:

```bash
./bin/ce
```

That starts the worker and the app, follows both logs, and stops both on Ctrl-C.
`./bin/ce stop` clears up a stray, `./bin/ce status` says what is running and
how the queue looks, and `./bin/ce start` returns you to the prompt instead of
tailing the logs. Stopping is always SIGTERM first: the worker finishes the
drawing it is on rather than leaving a half-written file.

The queue is a SQLite table, not a list in memory, which is what makes the rest
of it true. Close the tab and finished drawings stay finished. Restart the
worker mid-drawing and that drawing goes back to the queue rather than being
lost. Come back tomorrow, tick four more sheets, and the ones already read are
skipped.

| You press | What happens |
|---|---|
| Pause | the drawing in flight finishes, nothing new starts |
| Stop current | the worker notices between model calls and stops cleanly |
| Cancel waiting | queued drawings are dropped, the running one is left alone |
| Retry failed | failed and cancelled drawings go to the back of the queue |

Nothing is killed from outside. A job interrupted mid-write leaves a workbook
that looks finished and is not.

### A drawing is read once

Every extraction is cached under a hash of the PDF's bytes plus the profile, so
the second request for the same drawing is served in milliseconds. Copy a
drawing into another folder and it still hits. Reissue it under the same
filename and the hash changes, so it is read again — the mistake that matters
here is serving last revision's numbers without saying so.

`bin/worker.py --once` drains the queue and exits, which is the form to use from
cron or a test.

### Choosing what goes in the bill

Extraction and selection are separate steps on purpose. Reading is machine time
and happens over as many sittings as it takes; deciding what belongs in the BOQ
is an estimator's judgement and wants every line on one screen. Section 3 of the
Extract page lists every line item from every drawing read so far, filterable by
drawing and by source, with a tick box on each. The workbook is built from the
ticked lines only.

Results do not disappear. The download panel reads from disk and stays until you
press Clear.

## The workbook is linked, not copied

Each quantity in the Summary is a `SUMIF` into that drawing's own activity
sheet, and each `Qty (gross)` on an activity sheet is `net x (1 + wastage)`.
Correct a net quantity on `0107_Concrete` and three things follow on their own:
the gross beside it, that sheet's per-unit subtotal, and the Summary row and set
total above it.

The same holds for the items read from the drawing. A row whose quantity is
blank is the sheet stating a specification without an extent; type the area on
that drawing's `_Drawing items` sheet and it appears in the Summary.

One limit worth knowing. The link matches on the description, so a line your
team **adds** to a detail sheet with a description that is not already in the
Summary will total correctly on its own sheet but will not create a Summary row.
Copy an existing description if you want it to roll up.

## A missing figure never blocks the workbook

The Generate BOQ button used to be disabled unless the drawing produced a
pedestal or a grade slab. Five sheets in this set produce neither, so five
sheets produced nothing at all — and the figure that was missing stayed missing
either way.

Now the workbook is always produced, and what the drawing did not say goes on
its own **Gaps_and_Assumptions** sheet, right behind the Summary. Each row
carries four things: what is missing, what was used instead, what that affects,
and where to put the right answer. They are ranked by how the number should be
treated rather than by how bad it is:

| | Meaning |
|---|---|
| Not priced | the quantity is absent from the bill, not wrong in it |
| Assumed | a number is present and did not come off the drawing |
| Needs one figure from you | a specification with no extent; supply it and the row prices itself |
| For information | provenance worth knowing, nothing to do |

**Assumed** is the row to watch. It is the only class that looks exactly like
every other number in the bill.

## The app opens on the drawing

The entry script used to be a project-setup screen: typed fields for the
project name, drawing number, revision and date, beside a readiness panel. It
was the first thing anyone saw and it was the wrong first thing. Nobody opens
this tool to type a drawing number — they open it with a drawing, and the model
reads the number off the title block faster than a person can type it.

`Home.py` still exists, because Streamlit needs a script to start from and every
launcher and systemd unit names it, but it now checks the password and hands
straight over to **Drawing → BOQ**. It is hidden from the page list: a nav entry
that bounces you elsewhere the moment you click it reads as a bug. The identity
fields moved into that page's **Project details** box, and saving or loading a
project sits in the session bar at the top of it.

### Clear session

One button, above everything, resetting all three areas of the page at once:

| Area | What goes back to empty |
|---|---|
| 1 · Drawings | ticked drawings, the uploader's own file list, delete confirmations |
| 2 · Extraction | the extraction, the review grids, derivation rules, the workbook link |
| 3 · The BOQ | drawing and line selections, all filters, the search box, the built BOQ |

Two things are deliberately kept. The **saved extractions** under `output/cache`
stay, so a drawing cleared and queued again comes back in milliseconds rather
than minutes of model time. The **uploaded PDFs** stay too, behind an opt-in
tick, because a clear that silently deletes a morning's uploads is a button
nobody presses twice.

The finished queue rows *are* cleared, because section 3 is built from them —
leaving them would refill the section the moment the page redrew, which looks
exactly like the clear having failed.

## Searching the line items

Section 3 carries one search box across all four columns: drawing, source,
group and description. Every word you type has to appear somewhere in the row,
so `rebar 0107` narrows twice and word order does not matter. The drawing
filter below it is narrowed by whatever the box matched, so typing part of a
number and then picking from a short list beats scrolling a long one.

## Green field, brown field, repair

Each drawing carries a site classification, set from a dropdown on its row in
section 1. It is an input rather than something read off the sheet, because
nothing on a drawing reliably says which it is — and the three are tendered at
different rates. A pedestal on open ground, the same pedestal inside a running
plant, and making good one that already exists are the same cubic metre of
concrete at three different prices.

The choice is kept in `output/classifications.json`, keyed by file name rather
than by path: the app copies an upload into `output/uploads/`, so one drawing
routinely exists in two places, and a path key made those two copies two
different drawings. Keeping it on disk rather than in the session is what lets
`bin/rebuild_set.py` file a workbook correctly long after the browser tab has
gone.

### The Location Based Report

A new sheet in `SET_BOQ.xlsx`, sitting behind Summary and Drawings. Every other
sheet keeps exactly the content it had.

```
BROWN FIELD                                     4 drawing(s)
  Earthwork
    1  MD-522-8110-EG-CV-LAD-0106  Excavation …  m3   =SUMIF('0106_Earthwork'!…)
    2  MD-522-8120-EG-CV-LAD-0101  Excavation …  m3   =SUMIF('8120-0101_Earth'!…)
       Total Earthwork (Brown Field)             m3   =SUMIF($D$8:$D$11,…)
  Structural Concrete
    …
GREEN FIELD                                     9 drawing(s)
  …
ALL CLASSIFICATIONS
       Set total — m3                                 =$E$12+$E$28+…
```

Every component present is listed, not just pedestals and rebar, in the order a
foundation is built. Items the drawing merely specifies come last, because they
carry blank quantities more often than not and a report opening on forty rows
of "area not stated" reads as though nothing was extracted.

Nothing on the sheet is a copy. Each quantity is the same `SUMIF` into that
drawing's own activity sheet that the Summary already uses, and each total is a
formula over the rows above it — so a component holding both m³ and m² totals
each honestly instead of adding them together.

## Drawings are not in the repository

`Drawings/`, every PDF, and the generated project state are all ignored now.
They are the client's, they are large, and the tool is meant to run against
whatever set you point it at. The folder was already removed on GitHub; the
files were still tracked locally, so they have been untracked as well — they
remain on disk, but the next commit will not put them back.
